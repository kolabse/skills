Цей репозиторій - канонічне місце для навиків kolabse, що перевикористовуються.
Кожна навичка повинна залишатися сфокусованою, переносимою, атрибутованою і
придатний для незалежної установки.

## Перед додаванням навички

1. Визначте канонічний джерело і вирішите, чи володітиме репозиторій
   навичкою або дзеркало інше джерело.
2. Підтвердьте право розповсюджувати кожну скопійовану інструкцію, скрипт,
   довідковий матеріал та ресурс. Оригінальні матеріали приймаються за
   Apache-2.0, якщо не вказано інше. Зберігайте сторонні ліцензії,
   copyright, атрибуцію та повідомлення про зміни; вказуйте SPDX у каталозі.
   Не публікуйте матеріали з невирішеним ліцензуванням.
3. Знайдіть тригери, що перетинаються, в існуючих описах. Розширюйте навичку,
   якщо мета процесу та сама; створюйте новий при самостійному тригері та
   критерії завершення.
4. Виберіть рядкове ім'я, що починається з дієслова, через дефіси довжиною не більше
   63 символи.

Критерій завершення: до копіювання файлів відомі власник, походження,
ліцензія, область відповідальності та ім'я навички.

## Супровід кандидата до реалізації

Якщо нова або розширена навичка виникла з GitHub Issue, зберігайте Issue як
канонічну робочу задачу, доки реалізація не з'явиться в основній гілці.

1. Вкажіть вихідний Issue у pull request реалізації.
2. Додати`Closes #<issue-number>`в описі pull request. Якщо Issue не можна
   закривати, явно поясніть причину та подальшу долю.
3. Після злиття перевірте Issue, не покладаючись лише на ключове слово. Якщо він
   несподівано відкритий, закрийте як виконаний із посиланнями на PR та реліз.
4. Якщо реалізація відхилена, замінена або завершена частково, залиште
   пояснення та виберіть відповідний статус Issue. Наявність гілки чи PR не
   доводить завершення кандидата.

Критерій завершення: кожен реалізований кандидат простежується від Issue до
злитого PR, а Issue має перевірений підсумковий статус та пояснення результату.

## Додавання або перенесення навички

1. Синхронізуйте вихідний та цільовий репозиторії, не перезаписуючи локальну
   роботу.
2. Створіть`skills/<skill-name>/SKILL.md`. У frontmatter залиште тільки`name`і`description`; ім'я папки має збігатися з`name`.
3. Розміщуйте детерміновані помічники в`scripts/`, подробиці для агента
   в`references/`, вихідні матеріали - в`assets/`, необов'язкові UI-метадані
   - в`agents/openai.yaml`. Конфігурація проекту залишається поза папкою навички.
4. Пишіть наказові кроки з критеріями завершення, що перевіряються. Тіло має
   бути коротшим за 500 рядків; деталі окремих гілок виносьте у прямі посилання.
5. Додайте один запис до`skill-catalog.json`:
   - `name`та відносний шлях`path`;
   - рівно одну основну`category`з урахуванням документованого порядку
     пріоритету;
   - один або кілька контрольованих`tags`для етапу життєвого циклу,
     галузі дії, поведінки та інтеграцій;
   -`status`: `experimental`, `stable`або`deprecated`;
   - GitHub-імена в`maintainers`;
   - підтримувані`platforms`;
   - SPDX-вираз у`license`;
   - вид походження, джерело, колишні імена та канонічний репозиторій.
   Перевіряйте значення категорій та тегів за`schemas/skill-catalog.schema.json`; статус зрілості від них залежить.
6. Додайте навичку в каталог README з призначенням, встановленням та обов'язковим
   першою дією.
7. Додайте тести детермінованих скриптів та реалістичні позитивні та
   близькі негативні запити. Зберігайте мінімум по три випадки в`evals/<skill-name>.json`та вкажіть файл як`trigger_evals`у каталозі.

Для перенесеної навички зберігайте історію походження навіть після переходу
у цей репозиторій. Для vendored-навички фіксуйте незмінну ревізію
джерела, ліцензії та повідомлення; відокремлюйте upstream-зміни від локальних.
Перевіряйте сумісність ліцензій до об'єднання стороннього матеріалу з
Apache-2.0

Критерій завершення: читач може визначити джерело, власника, ліцензію,
середовища та спосіб перевірки навички.

## Контракт конфігурації

Кожна навичка, що настроюється, оголошує об'єкт`configuration`в`skill-catalog.json`і дотримується таких правил:

- `configure`зберігається як масив argv, безпечний при повторі, зберігає
  сторонній текст і змінює ідентичну конфігурацію;
-`status`працює read-only, підтримує машинний JSON, завершується успішно
  лише за коректної зміни і виводить секрети;
- область`project`або`user`вказано явно, конфігурація знаходиться поза
  встановленої папки навички;
- JSON/YAML-конфігурація має позитивну версію, JSON Schema та fail-closed
  команду міграції;
- керований текст використовує парні маркери навички, відхиляє пошкоджені
  або повторні маркери та не переписує решту тексту;
- Навички без стану використовують формат`none`, тільки read-only status і не
  створюють фіктивні файли конфігурації.

Команди зберігаються масивами, а не shell-рядками. Використовуйте placeholders на зразок`<project-root>`і ніколи не поміщайте облікові дані до команд каталогу.
Міграції мають бути послідовними та ідемпотентними; більше невідома
нову версію слід відхиляти, а не намагатися зменшити.

Критерій завершення: повторний configure дає побайтно ідентичний результат,
status нічого не записує, міграції зберігають підтримуване введення, тести
покривають відсутню, пошкоджену, поточну та застарілу конфігурацію.

## Збереження шляху оновлення споживачів

- Версії`.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`,
  `skill-catalog.json.collection_version`і всіх`skills/*/collection-metadata.json`повинні збігатися у релізі.
- Перевіряйте копіювану установку та оновлення з найстарішою підтримуваною
  версії закріпленим`skills`CLI для`codex`і`claude-code`.
- Встановлюйте колекцію для кожного агента глобально. Зберігайте конфігурацію,
  керовані правила та навмисні проектні налаштування поза встановленими навичками. Не
  створюйте конфігурацію невикористовуваної навички під час оновлення.
- Після оновлення виявляйте старі проектні копії та показуйте сповіщення
  про централізацію. Міграція має спочатку побудувати план без запису, перевірити
  глобальні копії до видалення, зберегти сторонні навички та налаштування,
  залишити резервну копію, що відновлюється, і запросити згоду на перевірений план.
- Документуйте міграції та обмеження відкату в README та changelog. Зниження
  конфігурація не підтримується без окремого тесту.
- При зміні персонального ринку зберігайте сторонні записи, додавайте
  один cachebuster до копії плагіна та вимагайте нове завдання Codex після активації.

Критерій завершення: споживач бачить версії, може оновити та мігрувати
конфігурацію, діагностувати змішані версії та перевстановити минулий тег.

## Збереження поведінки між агентами

Загальні`SKILL.md`і помічники повинні бути переносимими. Codex залишається
значенням за замовчуванням; явний Claude Code використовує`.claude/skills`,
`CLAUDE.md`і`/skill-name`. Не замінюйте існуючі`.agents`API заради
перейменування іншого споживача.

`agents/openai.yaml`- UI-метадані OpenAI,`.codex-plugin`- Упаковка Codex,
а Claude-упаковка знаходиться в`.claude-plugin`. Один manifest не підміняє
перевірку іншого. Якщо агент не підтримує можливість на кшталт перерахування
задач Codex Desktop, обмежена операція повинна завершуватися як unsupported,
зберігаючи ядро, що переноситься.

Критерій завершення: обидві глобальні установки містять однакові навички, дотримуються
нативні правила і layouts, значення Codex не змінені, а consumer-smoke
називає обох агентів.

## Композиція навичок за можливостями

Оголошуйте невеликі імена в`provides`, обов'язкові залежності в`requires`,
неблокуючі інтеграції в`optional_integrations`. Іменована композиція
потрібна тільки процесу, що повторюється мінімум з двох навичок. Її`required_steps`упорядковані, а`optional_steps`запускаються тільки коли
можливість включена проектом чи користувачем.

Не копіюйте процес однієї навички до іншої. Викликайте залежність, використовуйте
спостережуваний результат і зупиняйтеся, якщо обов'язкова можливість
недоступна. Необов'язкові повідомлення та журналування не перетворюють помилку на
успіх не змінюють успішний основний результат на неуспіх.

Критерій завершення: у кожної обов'язкової можливості є provider, кроки
посилаються на існуючі навички один раз, порядок покритий інтеграційним тестом
або здійсненним критерієм.

## Управління статусом життєвого циклу

- Нова або суттєво перероблена навичка залишається`experimental`, поки не
  пройдуть метадані, детерміновані помічники, cross-platform тести,
  development trigger corpus, незалежний forward-test, copied-install smoke та
  release holdout. Незастосовні вимоги можна назвати N/A.
-`stable`призначається тільки у версійному релізі колекції разом з`stable_since`. Stable гарантує сумісність документованих входів,
  конфігурації, safety boundaries та CLI в межах major-версії або інструкції
  міграції.
- Перед видаленням призначте`deprecated`, вкажіть заміну або міграцію та
  зберігайте навичку щонайменше один minor-реліз, крім термінової проблеми безпеки.

Критерій завершення: статус підтверджений перевіркою, що спостерігається, і ясно повідомляє
сумісність.

## Збереження походження встановлених навичок

Відоме ім'я навички – лише кандидат, а не ідентифікатор колекції. Звіряйте
джерело зовнішнього lock-файлу з`collection-metadata.json`. Нормалізуйте
підтримувані GitHub-форми до`https://github.com/kolabse/skills`; локальні
джерела перевіряйте по manifest, каталогу та вмісту навички без залежності
від імені Checkout.

Fail closed у збігаючому імені з іншого джерела або суперечливих
метаданих. Legacy adoption залишається явним і допускається лише за перевіреного
lock-джерелі; результатом повинні бути актуальні метадані та здорова діагностика.

Критерій завершення: status показує provenance, update вибирає тільки
перевірені навички або явно прийнятий legacy, тести покривають колізії,
release refs, перейменовані checkout та legacy-установки.

## Перевіряється автоматизація споживачів

`plan`залишається read-only: він не викликає установників, міграції та мережі.
Публікуйте версійні JSON Schema для plan/result та розрізняйте unchanged,
updated, migrated, skipped, blocked та failed без розбору людиночитаного CLI.

Обмежте глобальне виявлення документованих lock та instalation roots,
не скануйте домашній каталог. Застосовуйте ті самі правила provenance, явного
вибору та post-update діагностики.

Standalone bootstrap перевіряє checksum до розпакування, GitHub provenance до
виконання, відхиляє traversal і symlink entries, використовує тимчасову папку та
повертає код manager. Режим без attestation доступний тільки через явний
degraded-mode flag.

Критерій завершення: схеми читаються, dry-run не змінює fixtures, глобальні
fixtures покривають підтримувані та неоднозначні layouts, bootstrap smoke
проходить на всіх підтримуваних ОС.

## Перевірка зміни

Виконайте:

```shell
python scripts/validate_skills.py
python scripts/validate_localizations.py
python -m unittest discover -s tests -v
npx skills@1.5.22 add . --list
python scripts/smoke_install.py --agent codex
python scripts/smoke_install.py --agent claude-code
```

Перевірте trigger corpus на цьому агенті, включаючи перший запуск досвіду.
Структурний CI підтверджує повноту корпусу, але не замінює спостереження виклику
моделі. Додайте запити та результат у checklist pull request.

Для загальної trigger evaluation підготуйте blind suite та оцініть відповіді selector:

```shell
python scripts/trigger_evals.py prepare --output .trigger-evals/suite.json
python scripts/trigger_evals.py score \
  --predictions .trigger-evals/predictions.json \
  --json-output .trigger-evals/report.json \
  --markdown-output .trigger-evals/report.md
```

Selector може вибрати кілька навичок чи жодного. Не показуйте йому
вихідні eval-файли, очікувані labels, причини автора, передбачувані помилки та
попередні звіти. Фіксуйте provider/model, зберігайте raw predictions та
перевіряйте кожен false positive/negative. Зростання score не виправдовує розширення
тригера, що створює неоднозначність.

`evals/release-holdout-vN.json`- append-only release evidence. Не читайте та не
запускайте активний holdout під час налаштування описів. Опубліковані версії
незмінні: створюйте`vN+1`, оновлюйте ім'я, шлях і canonical digest, зберігайте
усі версії. Після заморожування описів запускайте holdout та порівнюйте з baseline
тієї ж версії та selector-конфігурації. Assertion digests повинні збігатися.
Прийнятий звіт зберігається в`evals/baselines/`, покажчик каталогу оновлюється.
Для недетермінованого selector використовуйте непарне число не менше трьох
незалежних blind runs та majority vote. Не можна повторювати один прогін до успіху
чи відкидати коректні неуспішні спостереження.

Критерій завершення: всі команди проходять на кожній підтримуваній ОС, а PR
checklist містить докази порушеної навички.

## Захист ланцюжка релізу

- Закріплюйте GitHub Actions повним SHA та залишайте версію у коментарі.
  Оновлення SHA проходять review через Dependabot.
- Видавайте`GITHUB_TOKEN`лише необхідні дозволи.
- Збирайте архіви через`scripts/build_release.py`та перевіряйте`SHA256SUMS`.
- Публікуйте GitHub artifact attestations для кожного asset і перевіряйте їх
  командою`gh attestation verify <artifact> --repo kolabse/skills`.

- Не замінюйте існуючий asset. Повторний workflow повинен підтвердити
  ідентичні байти або завершитися помилкою.
- не переміщуйте теги версій; виправлення публікується новою версією.

Критерій завершення: тег вказує на reviewed commit, assets збігаються з`SHA256SUMS`, Залежно від workflow закріплені незмінними посиланнями.
