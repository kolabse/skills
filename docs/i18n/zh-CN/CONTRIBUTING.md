本仓库是可复用 kolabse 技能的权威来源。每个技能都应保持聚焦、可移植、来源明确，并可独立安装。

## 添加技能之前

1. 确定权威来源。决定由本仓库拥有该技能，还是镜像其他来源。
2. 确认可重新分发每一份复制的指令、脚本、参考资料和资源。除非另有明确标记，原创贡献均依据仓库的 Apache-2.0 许可证接受。保留第三方许可证文件、版权声明、署名和修改声明；在目录中记录其 SPDX 表达式。不得发布许可证尚未明确的第三方材料。
3. 搜索现有描述，检查触发条件是否重叠。当工作流目的相同时，扩展现有技能；当存在独立有用的触发条件和完成标准时，才添加新技能。
4. 选择以动词开头、全小写、用连字符分隔且不超过 63 个字符的名称。

完成标准：复制文件前，已明确所有权、来源、许可证、范围和技能名称。

## 跟踪候选技能直至实现

当新技能或技能扩展源自 GitHub Issue 时，在实现进入主分支之前，始终将该 Issue 作为权威工作项。

1. 在实现的拉取请求中记录源 Issue。
2. 在拉取请求正文中添加 `Closes #<issue-number>`。如果该变更不应关闭 Issue，请明确说明原因和预期处理方式。
3. 合并后检查 Issue，不要假定关闭关键字已生效。如果它意外地仍处于打开状态，请将其作为已完成关闭，并附上实现的拉取请求链接，以及可用时的发布链接。
4. 如果实现被拒绝、被取代或仅部分交付，请留下解释性评论，并采用相应的 Issue 处理方式；绝不能仅因曾存在分支或拉取请求，就将候选技能报告为已完成。

完成标准：每个已实现的候选技能都可从源 Issue 追溯至已合并的拉取请求，且 Issue 的最终状态经过核实，并附有实现情况或未完成原因的说明。

## 添加或迁移技能

1. 同步源仓库和目标仓库，不覆盖本地工作。
2. 创建 `skills/<skill-name>/SKILL.md`。YAML 前置元数据中仅保留 `name` 和 `description`，并使文件夹名称与 `name` 一致。
3. 将确定性辅助程序放入 `scripts/`，面向代理的详细说明放入 `references/`，输出材料放入 `assets/`，可选的 UI 元数据放入 `agents/openai.yaml`。项目配置应保留在技能文件夹之外。
4. 使用祈使句编写步骤，并提供可检查的完成标准。正文保持在 500 行以下；分支专用的细节通过直接引用提供。
5. 在 `skill-catalog.json` 中添加一个条目：
   - `name` 和仓库相对 `path`；
   - 严格遵循文档所述优先顺序的唯一主要 `category`；
   - 一个或多个受控 `tags`，用于生命周期阶段、范围、行为和集成；
   - `status`：`experimental`、`stable` 或 `deprecated`；
   - `maintainers` 中的 GitHub 用户名；
   - 支持的 `platforms`；
   - `license` 中的 SPDX 表达式；
   - 来源类型、来源、曾用名称和权威仓库。
   依据 `schemas/skill-catalog.schema.json` 验证类别和标签值；成熟度状态独立于两者。
6. 将技能添加到 README 目录，并说明其用途、安装注意事项和必需的首次运行操作。
7. 为确定性脚本添加测试，并提供应该触发和不应该触发技能的真实提示词。在 `evals/<skill-name>.json` 中至少保存三个正例和三个相近的负例，并在 `skill-catalog.json` 中以 `trigger_evals` 引用该文件。

对于迁移的技能，即使本仓库成为权威来源，也要在目录中保留其历史。
对于随仓库分发的第三方技能，记录不可变的源修订版本，将许可证和声明保留在技能文件夹中，并将上游变更与本地补丁分开。
将第三方内容与 Apache-2.0 内容组合之前，应确认许可证兼容性。

完成标准：读者能够确定技能的来源、所有者、许可方式、运行平台以及验证方法。

## 配置约定

每个可配置技能都应在 `skill-catalog.json` 中声明 `configuration` 对象，并遵循以下规则：

- `configure` 是 argv 数组，可安全重复执行，保留无关的项目内容，并在相同的第二次执行时报告无变更；
- `status` 为只读，支持机器可读的 JSON，仅在声明的配置存在且有效时以零退出，并且绝不输出秘密信息；
- 明确区分项目范围和用户范围；配置保留在已安装技能目录之外；
- JSON 和 YAML 配置具有正整数版本号、描述其解码后文档的随附 JSON Schema，以及在无法确认安全时拒绝继续的迁移命令；
- 受管理文本使用成对的技能专用标记，拒绝格式错误或重复的标记，并且不重写其区块以外的文本。
- 无状态技能使用 `none` 格式，仅提供只读状态命令，不得凭空创建占位配置产物。

命令以数组而非 shell 字符串保存。对调用者提供的值，使用 `<project-root>` 等占位符，绝不在目录命令中放入凭据。
迁移步骤应增量执行且具有幂等性；遇到未知的更新版本应拒绝处理，而不是猜测如何降级。

完成标准：已有配置在重复配置后输出的字节完全相同；状态检查不执行写入；迁移保留受支持的输入；测试覆盖缺失、格式错误、当前和旧版配置。

## 保留使用方的更新路径

- 同一发布版本中，`.codex-plugin/plugin.json`、`.claude-plugin/plugin.json`、`skill-catalog.json.collection_version` 以及每个 `skills/*/collection-metadata.json` 的版本必须一致。
- 通过固定版本的 `skills` CLI，为 `codex` 和 `claude-code` 测试复制安装，以及从仍受支持的最早历史发布版本进行更新。
- 为每个代理全局安装集合。将项目/用户配置、托管规则和有意设置的项目专属选项保留在已安装技能文件夹之外。绝不让更新程序为未使用的技能静默创建配置。
- 更新后检测旧的项目级副本，并显示集中化通知。迁移必须先以只读方式生成计划，在删除前验证全局副本，保留无关技能和项目配置，留下可恢复的备份，并要求用户对已审核计划明确批准。
- 在 README 和变更日志中记录必需的迁移及回滚限制。除非经过测试，否则视配置降级为不受支持。
- 更改个人市场时保留无关条目。为已安装插件副本添加一个缓存失效后缀，并要求激活后新建 Codex 任务。

完成标准：使用方无需依赖仓库内部知识，就能识别已安装版本、更新、迁移现有配置、诊断混合版本，以及重新安装先前的标签版本。

## 保留跨代理行为

保持共享的 `SKILL.md` 指令和辅助程序可移植。现有命令行接口继续以 Codex 为默认目标；明确指定 Claude Code 时，使用 `.claude/skills`、`CLAUDE.md` 和 `/skill-name`。
不要仅为另一个使用方更名而替换现有 `.agents` 配置 API。

将 `agents/openai.yaml` 视为 OpenAI UI 元数据，将 `.codex-plugin` 视为 Codex 打包配置。
Claude 打包配置属于 `.claude-plugin`；任何一方的清单都不得静默代替另一方的验证。
当代理缺少 Codex Desktop 任务枚举等能力时，将该限定操作报告为不受支持，同时保留可移植的子集。

完成标准：两种使用方的全局安装包含相同的技能内容，遵循各自原生的项目规则和技能布局，Codex 默认值保持不变，且使用方冒烟测试证据明确点名两个代理。

## 按能力组合技能

在 `provides` 中声明简明的能力名称，在 `requires` 中声明强制前提条件，在 `optional_integrations` 中声明非阻塞集成。
只有至少包含两个技能的重复性工作流才添加具名的集合组合。其 `required_steps` 有序执行；仅在项目或用户启用相应能力时，才运行 `optional_steps`。

不要将一个技能的工作流复制到另一个技能中。应调用前提技能，使用其可观察的完成结果，并在必需能力不可用时停止。
可选通知或日志既不能将操作失败伪装为成功，也不能掩盖主要操作的失败；主要操作的成功也必须如实报告。

完成标准：每项必需能力都有提供者；组合步骤仅引用现有技能且每个技能只出现一次；执行顺序有集成测试或可执行的完成标准。

## 管理生命周期状态

- 新建或经过重大重新设计的技能应保持 `experimental`，直至其元数据、确定性辅助程序、跨平台测试、开发触发语料库、独立前向测试、复制安装冒烟测试和发布留出测试全部通过。不适用的要求，例如纯文字工作流的随附脚本，可以记录为不适用。
- 仅在带版本号的集合发布中将技能标记为 `stable`。添加 `stable_since` 并填入该发布版本。稳定意味着已记录的输入、配置位置、安全边界和 CLI 行为在当前集合主版本内保持兼容，或提供迁移指导。
- 移除技能之前，先将其标记为 `deprecated`。在技能和变更日志中说明受支持的替代方案或迁移路径，并至少保留一个次要版本，除非紧急安全问题要求提前移除。

完成标准：生命周期状态有可观察的验证作为依据，并传达清晰的兼容性预期。

## 保留已安装内容的来源信息

已知技能名称只能作为候选线索，绝不能作为集合身份。将外部锁文件中的来源与已安装的 `collection-metadata.json` 关联核对。
将受支持的 GitHub 地址写法规范化为 `https://github.com/kolabse/skills`；依据插件清单、目录和所请求的技能内容验证本地开发来源，不依赖检出目录名称。

遇到来自其他来源的同名技能或互相矛盾的元数据时，应拒绝继续。旧版接纳必须明确执行，且仅当锁文件来源本身已获验证时才允许；成功接纳必须以当前元数据及健康的更新后诊断结束。

完成标准：状态报告展示来源分类；更新仅选择已验证的技能（或已明确接纳的旧版技能）；测试覆盖来源冲突、发布引用、已更名的本地检出目录以及旧版安装。

## 保持使用方自动化可检查

保持 `plan` 只读：它不得调用安装程序、迁移或网络操作。
为计划和结果载荷发布带版本的 JSON Schema，并区分未更改、已更新、已迁移、已跳过、已阻塞和失败状态，无需解析面向人的 CLI 输出。

将全局发现限制在文档所述的锁文件和安装根目录。不要扫描主目录来寻找可能的安装。
在全局范围应用相同的来源验证、显式选择和更新后诊断规则。

独立引导程序必须在解压前验证归档校验和、在执行前验证 GitHub 构建来源、拒绝路径遍历和符号链接归档条目、使用临时目录，并传递管理器的退出码。
未认证的离线执行必须受显式降级模式标志控制。

完成标准：模式能够解析；试运行后测试夹具的字节完全不变；全局测试夹具覆盖受支持和有歧义的布局；引导程序冒烟测试在每个受支持的 CI 操作系统上通过。

## 验证变更

运行：

```shell
python scripts/validate_skills.py
python scripts/validate_localizations.py
python -m unittest discover -s tests -v
npx skills@1.5.22 add . --list
python scripts/smoke_install.py --agent codex
python scripts/smoke_install.py --agent claude-code
```

使用实际代理测试触发语料库，包括技能的首次运行路径。结构性 CI 检查能保持语料库完整，但不能代替观察模型调用。
在拉取请求中附上提示词和观察到的结果。

对于整个集合的触发评估，准备盲测套件并对选择器的观测结果评分：

```shell
python scripts/trigger_evals.py prepare --output .trigger-evals/suite.json
python scripts/trigger_evals.py score \
  --predictions .trigger-evals/predictions.json \
  --json-output .trigger-evals/report.json \
  --markdown-output .trigger-evals/report.md
```

选择器可以选择多个技能，也可以不选任何技能。不要向选择器透露源评估文件、预期标签、作者理由、疑似失败或先前报告。
在预测元数据中记录提供商/模型身份，将原始预测与审查证据一起保留，并在更改描述前检查每个假阳性和假阴性。
如果扩大触发范围会使相近工作流产生歧义，那么更高的分数不足以成为这样做的理由。

将 `evals/release-holdout-vN.json` 视为仅可追加的发布证据。调整描述时，不要读取或运行当前留出测试。
现有留出版本不可变：创建 `vN+1`，更新目录名称、路径和权威摘要值，并保留每个已发布版本。
仅在候选描述冻结后运行当前留出测试，再将其报告与使用同一留出版本及选择器配置生成的基线比较。
绝不比较断言摘要不同的报告。发布后，将接受的报告保留在 `evals/baselines/` 下，并更新目录的基线指针；基线文件是发布证据，不得重写。
当选择器不具确定性时，执行不少于三次的奇数次独立盲测，并比较多数投票聚合结果。
不得对单个观测反复运行直到通过，也不得丢弃有效的失败观测。

完成标准：每个命令在所有受支持的操作系统上通过，且拉取请求检查清单包含受影响技能的证据。

## 保护发布链

- 将每个外部 GitHub Action 固定到完整的提交 SHA，并在注释中保留其发布版本。让 Dependabot 提出经过审查的 SHA 更新。
- 仅向每个工作流授予其必需的 `GITHUB_TOKEN` 权限。
- 通过 `scripts/build_release.py` 构建发布归档；上传资源前验证 `SHA256SUMS`。
- 为每个发布资源发布 GitHub 产物认证，并通过 `gh attestation verify <artifact> --repo kolabse/skills` 验证。
- 绝不替换现有发布资源。重复运行工作流时，必须验证已发布的字节完全相同，否则失败。
- 保持版本标签不可变。以新版本发布修正，不得移动现有标签或替换其源提交。

完成标准：标签解析到经过审查的提交，上传的资源与 `SHA256SUMS` 一致，工作流依赖均为不可变引用。
