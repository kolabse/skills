このリポジトリは、再利用可能な kolabse スキルの正規の管理元です。
各スキルは、目的を絞り、移植可能で、出典を明示し、単独でインストールできるようにしてください。

## スキルを追加する前に

1. 正規のソースを特定します。このリポジトリがスキルを管理するのか、別のソースをミラーするのかを決めます。
2. コピーするすべての指示、スクリプト、参照資料、アセットについて、再頒布する権利を確認します。
   独自の貢献は、明示的な別記がない限り、リポジトリの Apache-2.0 ライセンスで受け入れます。
   第三者のライセンスファイル、著作権表示、帰属表示、変更通知を保持し、その SPDX 式をカタログに記録します。
   ライセンスが未確定の第三者の資料は公開しないでください。
3. 既存の説明から、重複するトリガーを探します。ワークフローの目的が同じなら既存のスキルを拡張し、
   独立して有用なトリガーと完了基準がある場合は新しいスキルを追加します。
4. 小文字で動詞から始まる、ハイフン区切りの名前を選び、63 文字以内にします。

完了基準：ファイルをコピーする前に、所有者、来歴、ライセンス、対象範囲、スキル名が判明していること。

## 候補を実装まで追跡する

新規スキルまたは既存スキルの拡張が GitHub Issue に由来する場合は、
実装が主要ブランチに反映されるまで、その Issue を正規の作業項目として扱います。

1. 実装のプルリクエストに、元の Issue を記録します。
2. プルリクエスト本文に `Closes #<issue-number>` を記載します。変更によって Issue を閉じてはいけない場合は、
   その理由と予定する扱いを明示します。
3. マージ後は、終了キーワードが適用されたと推測せずに Issue を確認します。
   想定外に開いたままであれば、実装のプルリクエストと、存在する場合はリリースへのリンクを添え、完了として閉じます。
4. 実装が却下された、別の実装に置き換えられた、または一部だけ提供された場合は、説明のコメントを残し、
   対応する Issue の処理区分を使用します。ブランチやプルリクエストが存在しただけで候補を完了と報告してはなりません。

完了基準：実装されたすべての候補を、元の Issue からマージ済みプルリクエストまで追跡でき、
Issue の最終状態が検証され、実装または未完了の説明があること。

## スキルの追加または移行

1. ローカル作業を上書きせずに、移行元と移行先の両方のリポジトリを同期します。
2. `skills/<skill-name>/SKILL.md` を作成します。YAML フロントマターには `name` と `description` だけを含め、
   フォルダー名を `name` と一致させます。
3. 決定的に動作するヘルパーを `scripts/`、エージェント向けの詳細を `references/`、
   出力用の素材を `assets/`、任意の UI メタデータを `agents/openai.yaml` に配置します。
   プロジェクト設定はスキルフォルダーの外に置きます。
4. 確認可能な完了基準を持つ手順を命令形で記述します。本文は 500 行未満に保ち、
   条件分岐ごとの詳細は直接参照する資料で提示します。
5. `skill-catalog.json` にエントリを 1 件追加します。
   - `name` とリポジトリ相対の `path`。
   - 文書化された優先順位に従う、ちょうど 1 つの主要な `category`。
   - ライフサイクル段階、対象範囲、動作、連携について、統制語彙から選んだ 1 つ以上の `tags`。
   - `status`：`experimental`、`stable`、または `deprecated`。
   - `maintainers` に GitHub ハンドル。
   - 対応する `platforms`。
   - `license` に SPDX 式。
   - 来歴の種類、ソース、以前の名前、正規のリポジトリ。
   カテゴリとタグの値を `schemas/skill-catalog.schema.json` に照らして検証します。
   成熟度ステータスはそのどちらとも独立しています。
6. 目的、インストール上の注意、初回実行時に必要な操作とともに、README のカタログにスキルを追加します。
7. 決定的に動作するスクリプトのテストと、スキルを起動すべき場合とすべきでない場合の現実的なプロンプトを追加します。
   少なくとも 3 件の肯定例と 3 件の近接する否定例を `evals/<skill-name>.json` に保存し、
   `skill-catalog.json` から `trigger_evals` として参照します。

移行したスキルについては、このリポジトリが正規の管理元になった後も、その履歴をカタログに保持します。
取り込んだ外部スキルについては、不変のソースリビジョンを記録し、ライセンスと通知をスキルフォルダーに保持し、
上流の変更とローカルパッチを分けて管理します。第三者のコンテンツと Apache-2.0 のコンテンツを組み合わせる前に、
ライセンスの互換性を確認してください。

完了基準：読者が、スキルの出所、所有者、ライセンス、実行環境、検証方法を判断できること。

## 設定の契約

設定可能なすべてのスキルは、`skill-catalog.json` に `configuration` オブジェクトを宣言し、
次の規則に従います。

- `configure` は argv 配列とし、安全に繰り返し実行でき、無関係なプロジェクト内容を保持し、
  同一条件での 2 回目の実行では変更なしと報告します。
- `status` は読み取り専用で、機械可読な JSON に対応し、宣言された設定が存在して有効な場合にのみ
  終了コード 0 を返し、秘密情報を決して出力しません。
- プロジェクトスコープとユーザースコープを明示し、設定はインストール済みのスキルディレクトリの外に保持します。
- JSON と YAML の設定には、正の整数のバージョン、デコード後の文書を記述する同梱の JSON Schema、
  安全側に停止する移行コマンドを用意します。
- 管理対象テキストには、対になったスキル固有のマーカーを使い、不正または重複したマーカーを拒否し、
  ブロック外のテキストを書き換えません。
- 状態を持たないスキルは形式 `none` を使用し、読み取り専用の状態確認コマンドだけを公開し、
  仮の設定成果物を作ってはなりません。

コマンドはシェル文字列ではなく配列として保存します。呼び出し側が提供する値には `<project-root>`
などのプレースホルダーを使用し、カタログのコマンドに認証情報を決して含めないでください。
移行手順は段階的かつ冪等にし、ダウングレード方法を推測せず、新しい未知のバージョンを拒否します。

完了基準：設定が存在する場合、configure を繰り返しても出力がバイト単位で同一であり、status は書き込みを行わず、
移行は対応する入力を保持し、設定の欠落、不正、現行、旧形式をテストが網羅していること。

## インストール先エージェントの更新経路を維持する

- リリースでは `.codex-plugin/plugin.json`、`.claude-plugin/plugin.json`、
  `skill-catalog.json.collection_version`、およびすべての `skills/*/collection-metadata.json`
  のバージョンを同一に保ちます。
- `codex` と `claude-code` の両方について、固定バージョンの `skills` CLI を使ったコピー方式のインストールと、
  対応する最も古い以前のリリースからの更新をテストします。
- コレクションは各エージェント向けにグローバルへインストールします。プロジェクト設定、管理ルール、
  意図的なプロジェクト固有設定は、インストール済みスキルフォルダーの外に保持します。
  更新処理が未使用スキルの設定を黙って作成することを認めてはなりません。
- 更新後に古いプロジェクトスコープのコピーを検出し、中央管理への移行通知を表示します。
  移行は書き込みなしで計画し、削除前にグローバルコピーを検証し、無関係なスキルと設定を保持し、
  復元可能なバックアップと、レビュー済み計画に結び付いた明示的な承認を必要とします。
- 必要な移行とロールバックの制約を README と変更履歴に記載します。
  テストしていない設定のダウングレードは未対応として扱います。
- 個人用マーケットプレイスを変更するときは、無関係なエントリを保持します。
  インストールされたプラグインのコピーにはキャッシュバスター接尾辞を 1 つ適用し、有効化後は新しい Codex タスクを必要とします。

完了基準：インストール先エージェントにおいて、リポジトリ内部の知識に頼らず、インストール済みバージョンの特定、
更新、既存設定の移行、混在バージョンの診断、以前のタグの再インストールができること。

## エージェント間の動作を維持する

共有の `SKILL.md` の指示とヘルパーは移植可能に保ちます。既存のコマンドラインインターフェイスでは
Codex を既定のままとし、Claude Code を明示的に対象とした場合は `.claude/skills`、`CLAUDE.md`、
`/skill-name` を使用します。別のインストール先エージェント用に名前を変えるだけのために、
既存の `.agents` 設定 API を置き換えてはなりません。

`agents/openai.yaml` は OpenAI の UI メタデータとして、`.codex-plugin` は Codex 用パッケージとして扱います。
Claude 用パッケージは `.claude-plugin` の下に置き、いずれのマニフェストも他方の検証を黙って代替してはなりません。
Codex Desktop のタスク列挙などの機能をエージェントが持たない場合は、移植可能な部分を維持しつつ、
その限定された操作を未対応として報告します。

完了基準：両エージェントのグローバルインストールに同一のスキルペイロードが含まれ、それぞれ固有のプロジェクトルールと
スキル配置が尊重され、Codex の既定値は変わらず、インストール先のスモークテスト証拠に両エージェントが明記されていること。

## 機能に基づいてスキルを組み合わせる

`provides` に小さな機能名を、`requires` に必須の前提条件を、`optional_integrations` に処理を妨げない
任意の連携を宣言します。名前付きのコレクション構成は、少なくとも 2 つのスキルを含む反復的なワークフローにのみ追加します。
その `required_steps` には順序があり、`optional_steps` はプロジェクトまたはユーザーが該当機能を有効にした場合にのみ実行します。

あるスキルのワークフローを別のスキルにコピーしてはなりません。前提となるスキルを呼び出し、
観測可能な完了結果を受け取り、必須機能を利用できない場合は停止します。
任意の通知やログ記録は、主要操作について成功を偽って報告したり、その失敗を隠したりしてはなりません。

完了基準：すべての必須機能に提供元があり、構成の各ステップが既存のスキルを一度ずつ参照し、
実行順序に統合テストまたは実行可能な完了基準があること。

## ライフサイクルステータスを管理する

- 新規または大幅に再設計したスキルは、メタデータ、決定的に動作するヘルパー、クロスプラットフォームテスト、
  開発用トリガーコーパス、独立した前向きテスト、コピー方式のインストールのスモークテスト、
  リリースホールドアウトがすべて合格するまで `experimental` に保ちます。
  文章のみのワークフローにおける同梱スクリプトなど、適用されない要件は該当なしとして記録できます。
- スキルを `stable` とするのは、バージョン付きのコレクションリリースでのみ行います。
  そのリリースバージョンを `stable_since` に追加します。安定とは、文書化された入力、設定の場所、
  安全上の制約、CLI の動作が、現在のコレクションのメジャーバージョン内で互換性を保つか、移行ガイダンスを提供することです。
- 削除する前にスキルを `deprecated` にします。スキルと変更履歴に、対応する代替または移行経路を記載し、
  緊急の安全上の問題で早期の削除が必要な場合を除き、少なくとも 1 回のマイナーリリースを通じて保持します。

完了基準：ライフサイクルステータスが観測可能な検証で裏付けられ、互換性について明確な期待を伝えていること。

## インストール済みスキルの来歴を保持する

既知のスキル名は候補にすぎず、コレクションの識別情報とはみなしません。
外部ロックのソースを、インストール済みの `collection-metadata.json` と照合します。
対応する GitHub の表記を `https://github.com/kolabse/skills` に正規化し、ローカル開発ソースは、
チェックアウトのディレクトリ名に依存せず、プラグインマニフェスト、カタログ、要求されたスキルの内容から検証します。

別のソースの同名スキルや矛盾したメタデータについては、安全側に停止します。
旧インストールの引き継ぎは明示的にし、ロックのソース自体を検証した場合にのみ許可します。
引き継ぎの成功には、現行メタデータと正常な更新後診断が必要です。

完了基準：status が来歴の分類を示し、update が検証済みのスキルだけ、または明示的に引き継いだ旧スキルだけを選択し、
ソースの衝突、リリース参照、名前変更したローカルチェックアウト、旧インストールをテストが網羅していること。

## インストール先の自動化を検査可能に保つ

`plan` は読み取り専用に保ち、インストーラー、移行、ネットワーク操作を呼び出してはなりません。
計画と結果のペイロード用にバージョン付き JSON Schema を公開し、人向け CLI 出力の解析に頼らず、
変更なし、更新済み、移行済み、スキップ、ブロック、失敗の各状態を区別します。

グローバルな検出は、文書化されたロックとインストールのルートに限定します。
インストール候補を探してホームディレクトリを走査してはなりません。
グローバルスコープにも、同じ来歴確認、明示的選択、更新後診断の規則を適用します。

単独のブートストラップは、展開前にアーカイブのチェックサムを確認し、実行前に GitHub のビルド来歴を検証し、
パストラバーサルやシンボリックリンクを含むアーカイブ項目を拒否し、一時ディレクトリを使い、
マネージャーの終了コードを伝播しなければなりません。アテステーション未検証のオフライン実行は、
明示的な機能制限モードのフラグを必須とします。

完了基準：スキーマを解析でき、ドライラン後もフィクスチャがバイト単位で同一であり、グローバル用フィクスチャが
対応レイアウトと曖昧なレイアウトを網羅し、対応するすべての CI オペレーティングシステムでブートストラップのスモークテストが合格すること。

## 変更を検証する

次を実行します。

```shell
python scripts/validate_skills.py
python scripts/validate_localizations.py
python -m unittest discover -s tests -v
npx skills@1.5.22 add . --list
python scripts/smoke_install.py --agent codex
python scripts/smoke_install.py --agent claude-code
```

スキルの初回実行経路を含め、実際のエージェントでトリガーコーパスを実行します。
CI の構造チェックはコーパスの完全性を保ちますが、モデルの呼び出しを観測する代わりにはなりません。
プロンプトと観測結果をプルリクエストに含めます。

コレクション全体のトリガー評価では、ブラインドスイートを準備し、セレクターの観測結果を採点します。

```shell
python scripts/trigger_evals.py prepare --output .trigger-evals/suite.json
python scripts/trigger_evals.py score \
  --predictions .trigger-evals/predictions.json \
  --json-output .trigger-evals/report.json \
  --markdown-output .trigger-evals/report.md
```

セレクターは複数のスキルを選択することも、何も選択しないこともできます。
評価元ファイル、期待ラベル、作成者の理由、疑われる失敗、過去のレポートをセレクターに見せてはなりません。
予測メタデータにプロバイダーとモデルの識別情報を記録し、生の予測をレビュー証拠とともに保持し、
説明を変更する前に、偽陽性と偽陰性をそれぞれ調査します。
近接するワークフローが曖昧になる場合、スコアが高いという理由だけでトリガーを広げてはなりません。

`evals/release-holdout-vN.json` は追記専用のリリース証拠として扱います。
説明を調整している間、現行ホールドアウトを読んだり実行したりしてはなりません。
既存のホールドアウトバージョンは不変です。`vN+1` を作成し、カタログの名前、パス、正規のダイジェストを更新し、
公開済みのすべてのバージョンを保持します。現行ホールドアウトは、候補の説明を凍結した後にのみ実行し、
同じホールドアウトバージョンとセレクター設定から生成したベースラインとレポートを比較します。
アサーションのダイジェストが異なるレポートを決して比較しないでください。
リリース後は、承認済みレポートを `evals/baselines/` の下に保持し、カタログのベースライン参照を更新します。
ベースラインファイルはリリース証拠であり、書き換えてはなりません。
セレクターが非決定的な場合は、3 回以上の奇数回の独立したブラインド実行を行い、多数決で集約した結果を比較します。
単一の観測が合格するまで再実行したり、有効な失敗観測を破棄したりしてはなりません。

完了基準：対応する各オペレーティングシステムですべてのコマンドが成功し、プルリクエストのチェックリストに
対象スキルの証拠が含まれていること。

## リリースチェーンを保護する

- すべての外部 GitHub Action を完全なコミット SHA に固定し、そのリリースバージョンをコメントに残します。
  レビュー対象となる SHA 更新は Dependabot に提案させます。
- 各ワークフローには、必要な `GITHUB_TOKEN` 権限だけを付与します。
- `scripts/build_release.py` でリリースアーカイブをビルドし、アセットをアップロードする前に `SHA256SUMS` を検証します。
- すべてのリリースアセットに GitHub アーティファクトアテステーションを公開し、
  `gh attestation verify <artifact> --repo kolabse/skills` で検証します。
- 既存のリリースアセットを置き換えてはなりません。ワークフローの再実行では、公開済みのバイト列が同一であることを検証するか、失敗しなければなりません。
- バージョンタグは不変に保ちます。既存のタグを移動したりソースコミットを置き換えたりせず、修正は新しいバージョンとして公開します。

完了基準：タグがレビュー済みコミットを指し、アップロードされたアセットが `SHA256SUMS` と一致し、
ワークフローの依存関係が不変の参照であること。
