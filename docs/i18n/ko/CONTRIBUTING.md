# 스킬 기여 안내

이 문서는 한국어 번역입니다. 내용이 다를 경우 [영어 원문](../../../CONTRIBUTING.md)이 기준입니다.

이 저장소는 재사용 가능한 kolabse 스킬의 공식 원본 저장소입니다.
각 스킬은 목적이 명확하고, 이식 가능하며, 출처를 확인할 수 있고, 독립적으로 설치할 수 있어야 합니다.

## 스킬을 추가하기 전에

1. 기준이 되는 원본을 확인하세요. 이 저장소가 스킬을 직접 관리할지 다른 원본을 미러링할지 결정하세요.
2. 복사하는 모든 지침, 스크립트, 참고 자료, 에셋을 재배포할 권리를 확인하세요.
   별도로 명시하지 않는 한 독창적인 기여는 저장소의 Apache-2.0 라이선스에 따라 받습니다.
   제삼자 라이선스 파일, 저작권 고지, 출처 표시, 수정 고지를 보존하고 카탈로그에
   SPDX 표현식을 기록하세요. 라이선스가 해결되지 않은 제삼자 자료는 게시하지 마세요.
3. 기존 설명에서 겹치는 호출 조건을 찾으세요. 워크플로의 목적이 같으면 기존 스킬을 확장하고,
   독립적으로 유용한 호출 조건과 완료 기준이 있으면 새 스킬을 추가하세요.
4. 모두 소문자이고 동사를 앞에 두며 하이픈으로 연결한 63자 이하의 이름을 선택하세요.

완료 기준: 파일을 복사하기 전에 소유권, 출처, 라이선스, 범위, 스킬 이름이 정해져 있습니다.

## 후보의 구현 과정 추적

새 스킬이나 기존 스킬의 확장이 GitHub Issue에서 시작되었다면, 구현이 기본 브랜치에
반영될 때까지 해당 Issue를 기준 작업 항목으로 유지하세요.

1. 구현 풀 리퀘스트에 원본 Issue를 기록하세요.
2. 풀 리퀘스트 본문에 `Closes #<issue-number>`를 넣으세요. 변경으로 Issue를 닫으면
   안 되는 경우 그 이유와 예정된 처리 방식을 명시하세요.
3. 병합 후에는 종료 키워드가 적용되었다고 가정하지 말고 Issue를 확인하세요.
   예상과 달리 열려 있다면 구현 풀 리퀘스트와 가능한 경우 릴리스의 링크를 첨부하여
   완료 상태로 닫으세요.
4. 구현이 거부되거나, 다른 작업으로 대체되거나, 일부만 제공되었다면 설명 댓글을 남기고
   적절한 Issue 처리 상태를 사용하세요. 브랜치나 풀 리퀘스트가 존재했다는 이유만으로
   후보를 완료했다고 보고하지 마세요.

완료 기준: 구현된 모든 후보를 원본 Issue에서 병합된 풀 리퀘스트까지 추적할 수 있고,
Issue의 최종 상태를 확인했으며 구현 또는 미완료 사유가 설명되어 있습니다.

## 스킬 추가 또는 이전

1. 로컬 작업을 덮어쓰지 않고 원본과 대상 저장소를 모두 동기화하세요.
2. `skills/<skill-name>/SKILL.md`를 만드세요. YAML 프런트매터에는 `name`과
   `description`만 남기고 폴더 이름을 `name`과 일치시키세요.
3. 결정적인 동작의 도우미는 `scripts/`, 에이전트용 상세 자료는 `references/`,
   출력 자료는 `assets/`, 선택적 UI 메타데이터는 `agents/openai.yaml`에 두세요.
   프로젝트 설정은 스킬 폴더 밖에 보관하세요.
4. 검증 가능한 완료 기준과 함께 명령형 절차를 작성하세요. 본문은 500줄 미만으로 유지하고,
   특정 분기에만 필요한 상세 내용은 직접 연결된 참고 자료로 제공하세요.
5. `skill-catalog.json`에 다음 항목 하나를 추가하세요.
   - `name`과 저장소 상대 경로인 `path`;
   - 문서화된 우선순위에 따른 정확히 하나의 기본 `category`;
   - 수명 주기 단계, 범위, 동작, 연동을 나타내는 통제된 `tags` 하나 이상;
   - `status`: `experimental`, `stable` 또는 `deprecated`;
   - `maintainers`의 GitHub 핸들;
   - 지원하는 `platforms`;
   - `license`의 SPDX 표현식;
   - 출처 유형, 원본, 이전 이름, 기준 저장소.
   범주와 태그 값을 `schemas/skill-catalog.schema.json`에 따라 검증하세요.
   성숙도 상태는 범주 및 태그와 별개입니다.
6. 목적, 설치 참고 사항, 필수 첫 실행 작업과 함께 스킬을 README 카탈로그에 추가하세요.
7. 결정적 스크립트의 테스트와 스킬을 호출해야 하는 상황 및 호출하지 않아야 하는 상황의
   현실적인 프롬프트를 추가하세요. `evals/<skill-name>.json`에 최소 세 개의 양성 사례와
   세 개의 유사한 음성 사례를 저장하고, `skill-catalog.json`에서 해당 파일을
   `trigger_evals`로 참조하세요.

이전된 스킬은 이 저장소가 기준 원본이 된 후에도 카탈로그에 이력을 보존하세요.
외부에서 포함한 스킬은 변경 불가능한 원본 리비전을 기록하고, 라이선스와 고지를
스킬 폴더에 보관하며, 업스트림 변경을 로컬 패치와 분리하세요. 제삼자 콘텐츠를
Apache-2.0 콘텐츠와 결합하기 전에 라이선스 호환성을 확인하세요.

완료 기준: 독자가 스킬의 출처, 소유자, 라이선스, 실행 환경, 검증 방법을 확인할 수 있습니다.

## 설정 계약

설정 가능한 모든 스킬은 `skill-catalog.json`에 `configuration` 객체를 선언하고
다음 규칙을 따릅니다.

- `configure`는 argv 배열이며 안전하게 반복 실행할 수 있어야 합니다. 관련 없는 프로젝트
  내용을 보존하고, 동일한 두 번째 실행에서는 변경이 없다고 보고해야 합니다.
- `status`는 읽기 전용이며 기계 판독 가능한 JSON을 지원해야 합니다. 선언된 설정이
  존재하고 유효할 때만 종료 코드 0을 반환하며 비밀 정보를 출력해서는 안 됩니다.
- 프로젝트와 사용자 범위를 명시하고, 설정은 설치된 스킬 디렉터리 밖에 보관하세요.
- JSON 및 YAML 설정에는 양의 정수 버전, 디코딩된 문서를 설명하는 번들 JSON Schema,
  검증 실패 시 진행을 차단하는 마이그레이션 명령이 있어야 합니다.
- 관리되는 텍스트에는 스킬별로 쌍을 이루는 마커를 사용하고, 잘못되거나 중복된 마커를
  거부하며, 블록 밖의 텍스트는 다시 쓰지 마세요.
- 상태를 유지하지 않는 스킬은 `none` 형식을 사용하고 읽기 전용 상태 명령만 제공하며,
  임시로 자리를 채우는 설정 산출물을 만들어서는 안 됩니다.

명령은 셸 문자열이 아닌 배열로 저장하세요. 호출자가 제공하는 값에는 `<project-root>`
같은 자리표시자를 사용하고, 카탈로그 명령에 자격 증명을 넣지 마세요. 마이그레이션 단계는
점진적이고 멱등적이어야 하며, 알 수 없는 새 버전은 다운그레이드 방법을 추측하지 말고 거부하세요.

완료 기준: 기존 설정에서 configure를 반복 실행하면 바이트 단위로 동일한 출력이 생성되고,
status는 쓰기를 수행하지 않으며, 마이그레이션은 지원하는 입력을 보존하고, 테스트는
누락되거나 잘못된 설정, 현재 설정, 레거시 설정을 포함합니다.

## 에이전트 설치 환경의 업데이트 경로 보존

- 릴리스에서 `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`,
  `skill-catalog.json.collection_version`, 모든 `skills/*/collection-metadata.json`의
  버전을 동일하게 유지하세요.
- `codex`와 `claude-code` 모두에 대해 고정된 `skills` CLI로 복사 설치와
  지원하는 가장 오래된 이전 릴리스에서의 업데이트를 테스트하세요.
- 모음은 각 에이전트에 전역으로 설치하세요. 프로젝트 및 사용자 설정, 관리되는 규칙,
  의도적인 프로젝트별 설정은 설치된 스킬 폴더 밖에 보관하세요. 업데이터가 사용하지 않는
  스킬의 설정을 알리지 않고 만들게 해서는 안 됩니다.
- 업데이트 후 기존 프로젝트 범위 복사본을 감지하고 중앙화 안내를 표시하세요.
  마이그레이션은 쓰기 없이 계획하고, 삭제 전에 전역 복사본을 검증하며, 관련 없는 스킬과
  프로젝트 설정을 보존하고, 복구 가능한 백업과 검토한 계획에 묶인 명시적 승인을 요구해야 합니다.
- 필수 마이그레이션과 롤백 제한을 README 및 변경 이력에 문서화하세요.
  테스트하지 않은 설정 다운그레이드는 지원되지 않는 것으로 취급하세요.
- 개인 마켓플레이스를 변경할 때 관련 없는 항목을 보존하세요. 설치된 플러그인 복사본에
  캐시 갱신용 접미사 하나를 적용하고, 활성화 후 새 Codex 작업을 시작하도록 요구하세요.

완료 기준: 에이전트 설치 환경에서 저장소 내부 지식에 의존하지 않고 설치 버전 식별,
업데이트, 기존 설정 마이그레이션, 혼합 버전 진단, 이전 태그 재설치를 수행할 수 있습니다.

## 에이전트 간 동작 보존

공유 `SKILL.md` 지침과 도우미의 이식성을 유지하세요. 기존 명령줄 인터페이스의 기본값은
계속 Codex이며, 명시적인 Claude Code 대상은 `.claude/skills`, `CLAUDE.md`,
`/skill-name`을 사용합니다. 다른 대상 에이전트에 맞춰 이름만 바꾸기 위해 기존
`.agents` 설정 API를 교체하지 마세요.

`agents/openai.yaml`은 OpenAI UI 메타데이터로, `.codex-plugin`은 Codex 패키징으로
취급하세요. Claude 패키징은 `.claude-plugin`에 둡니다. 어느 매니페스트도 다른 쪽의
검증을 암묵적으로 대신해서는 안 됩니다. Codex Desktop 작업 열거와 같은 기능이 없는
에이전트에서는 이식 가능한 부분은 유지하면서 해당 한정된 작업을 지원하지 않는다고 보고하세요.

완료 기준: 두 에이전트의 전역 설치에 동일한 스킬 페이로드가 포함되고, 각각의 기본 프로젝트
규칙과 스킬 배치를 따르며, Codex 기본값은 바뀌지 않고, 대상별 스모크 테스트 증거에
두 에이전트 이름이 명시되어 있습니다.

## 기능에 따른 스킬 조합

작은 단위의 기능 이름을 `provides`에, 필수 전제 조건을 `requires`에, 진행을 차단하지 않는
연동을 `optional_integrations`에 선언하세요. 두 개 이상의 스킬을 사용하는 반복적인
워크플로에만 이름 있는 모음 조합을 추가하세요. `required_steps`에는 순서가 있으며,
`optional_steps`는 프로젝트나 사용자가 해당 기능을 활성화한 경우에만 실행합니다.

한 스킬의 워크플로를 다른 스킬에 복사하지 마세요. 필수 스킬을 호출하고 관찰 가능한
완료 결과를 사용하며, 필수 기능을 사용할 수 없으면 중단하세요. 선택적 알림이나 로깅이
성공한 기본 작업의 결과를 거짓 성공으로 바꾸거나 실패를 숨기게 해서는 안 됩니다.

완료 기준: 모든 필수 기능에 제공자가 있고, 조합 단계가 기존 스킬을 한 번씩 참조하며,
순서에 대한 통합 테스트 또는 실행 가능한 완료 기준이 있습니다.

## 수명 주기 상태 관리

- 새 스킬이나 실질적으로 재설계한 스킬은 메타데이터, 결정적 도우미, 교차 플랫폼 테스트,
  개발용 호출 조건 코퍼스, 독립적인 전향 테스트, 복사 설치 스모크 테스트, 릴리스 홀드아웃이
  모두 통과할 때까지 `experimental`로 유지하세요. 텍스트 지침만 있는 워크플로의 번들
  스크립트처럼 적용되지 않는 요구 사항은 해당 없음으로 기록할 수 있습니다.
- 버전이 지정된 모음 릴리스에서만 스킬을 `stable`로 표시하세요. 해당 릴리스 버전으로
  `stable_since`를 추가하세요. 안정 상태는 문서화된 입력, 설정 위치, 안전 경계, CLI 동작이
  현재 모음의 주 버전 안에서 호환성을 유지하거나 마이그레이션 안내를 제공한다는 뜻입니다.
- 제거 전에 스킬을 `deprecated`로 표시하세요. 스킬과 변경 이력에 지원되는 대체 스킬 또는
  마이그레이션 경로를 명시하고, 긴급한 안전 문제로 더 빠른 제거가 필요한 경우가 아니라면
  최소 한 번의 부 버전 릴리스 동안 유지하세요.

완료 기준: 수명 주기 상태는 관찰 가능한 검증으로 뒷받침되고 명확한 호환성 기대치를 전달합니다.

## 설치 출처 보존

알려진 스킬 이름은 후보로만 취급하고, 절대 모음의 정체성으로 간주하지 마세요.
외부 잠금 파일의 원본과 설치된 `collection-metadata.json`을 서로 대조하세요.
지원되는 GitHub 표기법은 `https://github.com/kolabse/skills`로 정규화하고,
로컬 개발 원본은 체크아웃 디렉터리 이름에 의존하지 않고 플러그인 매니페스트,
카탈로그, 요청된 스킬 내용으로 검증하세요.

다른 원본의 동명 스킬이나 모순되는 메타데이터가 있으면 안전하게 진행을 차단하세요.
레거시 설치 채택은 명시적으로 수행하고 잠금 파일의 원본 자체가 검증된 경우에만 허용하세요.
성공적인 채택은 최신 메타데이터와 정상적인 업데이트 후 진단으로 끝나야 합니다.

완료 기준: 상태 출력에 출처 분류가 나타나고, 업데이트는 검증된 스킬 또는 명시적으로
채택한 레거시 스킬만 선택하며, 테스트는 원본 충돌, 릴리스 참조, 이름이 바뀐 로컬
체크아웃, 레거시 설치를 포함합니다.

## 에이전트 설치 자동화의 검사 가능성 유지

`plan`은 읽기 전용으로 유지하세요. 설치 프로그램, 마이그레이션 또는 네트워크 작업을
호출해서는 안 됩니다. 계획 및 결과 페이로드용 버전 지정 JSON Schema를 게시하고,
사람이 읽는 CLI 출력을 파싱하지 않고도 변경 없음, 업데이트됨, 마이그레이션됨,
건너뜀, 차단됨, 실패 상태를 구분하세요.

전역 검색 범위를 문서화된 잠금 파일 및 설치 루트로 제한하세요. 설치본을 찾기 위해
홈 디렉터리를 훑지 마세요. 전역 범위에서도 동일한 출처, 명시적 선택, 업데이트 후 진단
규칙을 적용하세요.

독립 실행형 부트스트랩은 압축 해제 전에 아카이브 체크섬을 검증하고, 실행 전에
GitHub 빌드 출처를 검증하며, 경로 탐색과 심볼릭 링크 아카이브 항목을 거부하고,
임시 디렉터리를 사용하며, 관리자의 종료 코드를 전달해야 합니다. 증명 없는 오프라인
실행은 명시적인 보장 수준 저하 모드 플래그로만 허용하세요.

완료 기준: 스키마가 파싱되고, 시험 실행은 픽스처를 바이트 단위로 동일하게 유지하며,
전역 픽스처는 지원되는 배치와 모호한 배치를 포함하고, 부트스트랩 스모크 테스트가
지원하는 모든 CI 운영 체제에서 통과합니다.

## 변경 검증

다음을 실행하세요.

```shell
python scripts/validate_skills.py
python scripts/validate_localizations.py
python -m unittest discover -s tests -v
npx skills@1.5.22 add . --list
python scripts/smoke_install.py --agent codex
python scripts/smoke_install.py --agent claude-code
```

스킬의 첫 실행 경로를 포함하여 실제 에이전트에 호출 조건 코퍼스를 적용하세요.
구조적 CI 검사는 코퍼스의 완전성을 유지하지만 모델 호출을 직접 관찰하는 일을
대신하지는 못합니다. 프롬프트와 관찰 결과를 풀 리퀘스트에 포함하세요.

모음 전체의 호출 조건 평가를 위해 블라인드 테스트 모음을 준비하고 선택기의 관찰 결과를 채점하세요.

```shell
python scripts/trigger_evals.py prepare --output .trigger-evals/suite.json
python scripts/trigger_evals.py score \
  --predictions .trigger-evals/predictions.json \
  --json-output .trigger-evals/report.json \
  --markdown-output .trigger-evals/report.md
```

선택기는 여러 스킬을 선택하거나 하나도 선택하지 않을 수 있습니다. 원본 평가 파일,
예상 레이블, 작성자의 이유, 의심되는 실패, 이전 보고서를 선택기에 노출하지 마세요.
예측 메타데이터에 제공업체와 모델의 식별 정보를 기록하고, 원시 예측을 검토 증거와 함께
보관하며, 설명을 변경하기 전에 각 거짓 양성과 거짓 음성을 살펴보세요. 호출 조건을
넓히면 인접한 워크플로가 모호해지는 경우, 높은 점수만으로는 범위를 넓힐 이유가 되지 않습니다.

`evals/release-holdout-vN.json`은 추가만 가능한 릴리스 증거로 취급하세요.
설명을 조정하는 동안 활성 홀드아웃을 읽거나 실행하지 마세요. 기존 홀드아웃 버전은
변경 불가능합니다. `vN+1`을 만들고 카탈로그의 이름, 경로, 기준 다이제스트를 갱신하며,
게시된 모든 버전을 보존하세요. 후보 설명이 고정된 후에만 활성 홀드아웃을 실행하고,
동일한 홀드아웃 버전과 선택기 설정에서 생성한 기준 보고서와 비교하세요.
검증 항목 다이제스트가 다른 보고서는 절대 비교하지 마세요. 릴리스 후에는 승인된 보고서를
`evals/baselines/` 아래에 보존하고 카탈로그의 기준 보고서 포인터를 갱신하세요.
기준 보고서 파일은 릴리스 증거이므로 다시 작성해서는 안 됩니다.
선택기가 비결정적이면 최소 세 번 이상, 홀수 회의 독립적인 블라인드 실행을 수행하고
다수결 집계 결과를 비교하세요. 단일 관찰이 통과할 때까지 재실행하거나 유효한 실패
관찰 결과를 버리지 마세요.

완료 기준: 지원하는 각 운영 체제에서 모든 명령이 통과하고, 풀 리퀘스트 체크리스트에
영향을 받는 스킬의 증거가 포함되어 있습니다.

## 릴리스 체인 보호

- 모든 외부 GitHub Action을 전체 커밋 SHA로 고정하고 주석에 릴리스 버전을 남기세요.
  Dependabot이 검토를 거칠 SHA 업데이트를 제안하도록 하세요.
- 각 워크플로에는 필요한 `GITHUB_TOKEN` 권한만 부여하세요.
- `scripts/build_release.py`로 릴리스 아카이브를 만들고, 에셋을 업로드하기 전에
  `SHA256SUMS`를 검증하세요.
- 모든 릴리스 에셋에 대해 GitHub 산출물 증명을 게시하고
  `gh attestation verify <artifact> --repo kolabse/skills`로 검증하세요.
- 기존 릴리스 에셋을 절대 교체하지 마세요. 워크플로를 재실행할 때는 게시된 바이트가
  동일함을 검증하거나 실패해야 합니다.
- 버전 태그는 변경 불가능하게 유지하세요. 기존 태그를 이동하거나 원본 커밋을 교체하는
  대신 새 버전으로 수정 사항을 게시하세요.

완료 기준: 태그가 검토된 커밋을 가리키고, 업로드된 에셋이 `SHA256SUMS`와 일치하며,
워크플로 의존성은 변경 불가능한 참조입니다.
