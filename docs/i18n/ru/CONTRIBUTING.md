Этот репозиторий — каноническое место для переиспользуемых навыков kolabse.
Каждый навык должен оставаться сфокусированным, переносимым, атрибутируемым и
пригодным для независимой установки.

## Перед добавлением навыка

1. Определите канонический источник и решите, будет ли репозиторий владеть
   навыком или зеркалировать другой источник.
2. Подтвердите право распространять каждую скопированную инструкцию, скрипт,
   справочный материал и ресурс. Оригинальные материалы принимаются по
   Apache-2.0, если явно не указано иное. Сохраняйте сторонние лицензии,
   copyright, атрибуцию и уведомления об изменениях; указывайте SPDX в каталоге.
   Не публикуйте материалы с неразрешённым лицензированием.
3. Найдите пересекающиеся триггеры в существующих описаниях. Расширяйте навык,
   если цель процесса та же; создавайте новый при самостоятельном триггере и
   критерии завершения.
4. Выберите строчное, начинающееся с глагола имя через дефисы длиной не более
   63 символов.

Критерий завершения: до копирования файлов известны владелец, происхождение,
лицензия, область ответственности и имя навыка.

## Сопровождение кандидата до реализации

Если новый или расширенный навык возник из GitHub Issue, сохраняйте Issue как
каноническую рабочую задачу, пока реализация не появится в основной ветке.

1. Укажите исходный Issue в pull request реализации.
2. Добавьте `Closes #<issue-number>` в описание pull request. Если Issue нельзя
   закрывать, явно объясните причину и дальнейшую судьбу.
3. После слияния проверьте Issue, не полагаясь только на ключевое слово. Если он
   неожиданно открыт, закройте как выполненный со ссылками на PR и релиз.
4. Если реализация отклонена, заменена или завершена частично, оставьте
   объяснение и выберите соответствующий статус Issue. Наличие ветки или PR не
   доказывает завершение кандидата.

Критерий завершения: каждый реализованный кандидат прослеживается от Issue до
слитого PR, а Issue имеет проверенный итоговый статус и объяснение результата.

## Добавление или перенос навыка

1. Синхронизируйте исходный и целевой репозитории, не перезаписывая локальную
   работу.
2. Создайте `skills/<skill-name>/SKILL.md`. Во frontmatter оставьте только
   `name` и `description`; имя папки должно совпадать с `name`.
3. Размещайте детерминированные помощники в `scripts/`, подробности для агента —
   в `references/`, выходные материалы — в `assets/`, необязательные UI-метаданные
   — в `agents/openai.yaml`. Конфигурация проекта остаётся вне папки навыка.
4. Пишите повелительные шаги с проверяемыми критериями завершения. Тело должно
   быть короче 500 строк; детали отдельных ветвей выносите в прямые ссылки.
5. Добавьте одну запись в `skill-catalog.json`:
   - `name` и относительный путь `path`;
   - ровно одну основную `category` с учётом документированного порядка
     приоритета;
   - один или несколько контролируемых `tags` для этапа жизненного цикла,
     области действия, поведения и интеграций;
   - `status`: `experimental`, `stable` или `deprecated`;
   - GitHub-имена в `maintainers`;
   - поддерживаемые `platforms`;
   - SPDX-выражение в `license`;
   - вид происхождения, источник, прежние имена и канонический репозиторий.
   Проверяйте значения категорий и тегов по
   `schemas/skill-catalog.schema.json`; статус зрелости от них не зависит.
6. Добавьте навык в каталог README с назначением, установкой и обязательным
   первым действием.
7. Добавьте тесты детерминированных скриптов и реалистичные положительные и
   близкие отрицательные запросы. Храните минимум по три случая в
   `evals/<skill-name>.json` и укажите файл как `trigger_evals` в каталоге.

Для перенесённого навыка сохраняйте историю происхождения даже после перехода
в этот репозиторий. Для vendored-навыка фиксируйте неизменяемую ревизию
источника, лицензии и уведомления; отделяйте upstream-изменения от локальных.
Проверяйте совместимость лицензий до объединения стороннего материала с
Apache-2.0.

Критерий завершения: читатель может определить источник, владельца, лицензию,
поддерживаемые среды и способ проверки навыка.

## Контракт конфигурации

Каждый настраиваемый навык объявляет объект `configuration` в
`skill-catalog.json` и соблюдает следующие правила:

- `configure` хранится как массив argv, безопасен при повторе, сохраняет
  посторонний текст и не меняет идентичную конфигурацию;
- `status` работает read-only, поддерживает машинный JSON, завершается успешно
  только при корректной конфигурации и не выводит секреты;
- область `project` или `user` указана явно, конфигурация находится вне
  установленной папки навыка;
- JSON/YAML-конфигурация имеет положительную версию, JSON Schema и fail-closed
  команду миграции;
- управляемый текст использует парные маркеры навыка, отклоняет повреждённые
  или повторные маркеры и не переписывает остальной текст;
- навыки без состояния используют формат `none`, только read-only status и не
  создают фиктивных файлов конфигурации.

Команды хранятся массивами, а не shell-строками. Используйте placeholders вроде
`<project-root>` и никогда не помещайте учётные данные в команды каталога.
Миграции должны быть последовательными и идемпотентными; неизвестную более
новую версию следует отклонять, а не пытаться понизить.

Критерий завершения: повторный configure даёт побайтно идентичный результат,
status ничего не записывает, миграции сохраняют поддерживаемый ввод, тесты
покрывают отсутствующую, повреждённую, текущую и устаревшую конфигурацию.

## Сохранение пути обновления потребителей

- Версии `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json`,
  `skill-catalog.json.collection_version` и всех
  `skills/*/collection-metadata.json` должны совпадать в релизе.
- Проверяйте копируемую установку и обновление с самой старой поддерживаемой
  версии закреплённым `skills` CLI для `codex` и `claude-code`.
- Храните конфигурацию проекта и пользователя вне установленных навыков. Не
  создавайте конфигурацию неиспользуемого навыка при обновлении.
- Документируйте миграции и ограничения отката в README и changelog. Понижение
  конфигурации не поддерживается без отдельного теста.
- При изменении personal marketplace сохраняйте посторонние записи, добавляйте
  один cachebuster к копии плагина и требуйте новую задачу Codex после активации.

Критерий завершения: потребитель видит версии, может обновить и мигрировать
конфигурацию, диагностировать смешанные версии и переустановить прошлый тег.

## Сохранение поведения между агентами

Общие `SKILL.md` и помощники должны быть переносимыми. Codex остаётся
значением по умолчанию; явный Claude Code использует `.claude/skills`,
`CLAUDE.md` и `/skill-name`. Не заменяйте существующие `.agents` API ради
переименования для другого потребителя.

`agents/openai.yaml` — UI-метаданные OpenAI, `.codex-plugin` — упаковка Codex,
а Claude-упаковка находится в `.claude-plugin`. Один manifest не подменяет
проверку другого. Если агент не поддерживает возможность вроде перечисления
задач Codex Desktop, ограниченная операция должна завершаться как unsupported,
сохраняя переносимое ядро.

Критерий завершения: обе установки содержат одинаковые навыки, соблюдают
нативные правила и layouts, значения Codex не изменены, а consumer-smoke
называет обоих агентов.

## Композиция навыков по возможностям

Объявляйте небольшие имена в `provides`, обязательные зависимости в `requires`,
неблокирующие интеграции в `optional_integrations`. Именованная композиция
нужна только повторяющемуся процессу минимум из двух навыков. Её
`required_steps` упорядочены, а `optional_steps` запускаются только когда
возможность включена проектом или пользователем.

Не копируйте процесс одного навыка в другой. Вызывайте зависимость, используйте
наблюдаемый результат и останавливайтесь, если обязательная возможность
недоступна. Необязательные уведомления и журналирование не превращают ошибку в
успех и не меняют успешный основной результат на неуспех.

Критерий завершения: у каждой обязательной возможности есть provider, шаги
ссылаются на существующие навыки один раз, порядок покрыт интеграционным тестом
или исполнимым критерием.

## Управление статусом жизненного цикла

- Новый или существенно переработанный навык остаётся `experimental`, пока не
  пройдут метаданные, детерминированные помощники, cross-platform тесты,
  development trigger corpus, независимый forward-test, copied-install smoke и
  release holdout. Неприменимые требования можно отметить как N/A.
- `stable` назначается только в версионированном релизе коллекции вместе со
  `stable_since`. Stable гарантирует совместимость документированных входов,
  конфигурации, safety boundaries и CLI в пределах major-версии либо инструкции
  миграции.
- Перед удалением назначьте `deprecated`, укажите замену или миграцию и
  сохраняйте навык минимум один minor-релиз, кроме срочной проблемы безопасности.

Критерий завершения: статус подтверждён наблюдаемой проверкой и ясно сообщает
совместимость.

## Сохранение происхождения установленных навыков

Известное имя навыка — только кандидат, а не идентификатор коллекции. Сверяйте
источник внешнего lock-файла с `collection-metadata.json`. Нормализуйте
поддерживаемые GitHub-формы к `https://github.com/kolabse/skills`; локальные
источники проверяйте по manifest, каталогу и содержимому навыка без зависимости
от имени checkout.

Fail closed при совпадающем имени из другого источника или противоречивых
метаданных. Legacy adoption остаётся явным и допускается только при проверенном
lock-источнике; итогом должны быть актуальные метаданные и здоровая диагностика.

Критерий завершения: status показывает provenance, update выбирает только
проверенные навыки или явно принятый legacy, тесты покрывают коллизии,
release refs, переименованные checkout и legacy-установки.

## Проверяемая автоматизация потребителей

`plan` остаётся read-only: он не вызывает установщики, миграции и сеть.
Публикуйте версионированные JSON Schema для plan/result и различайте unchanged,
updated, migrated, skipped, blocked и failed без разбора человекочитаемого CLI.

Ограничьте глобальное обнаружение документированными lock и installation roots,
не сканируйте домашний каталог. Применяйте те же правила provenance, явного
выбора и post-update диагностики.

Standalone bootstrap проверяет checksum до распаковки, GitHub provenance до
выполнения, отклоняет traversal и symlink entries, использует временную папку и
возвращает код manager. Режим без attestation доступен только через явный
degraded-mode flag.

Критерий завершения: схемы читаются, dry-run не меняет fixtures, глобальные
fixtures покрывают поддерживаемые и неоднозначные layouts, bootstrap smoke
проходит на всех поддерживаемых ОС.

## Проверка изменения

Выполните:

```shell
python scripts/validate_skills.py
python scripts/validate_localizations.py
python -m unittest discover -s tests -v
npx skills@1.5.22 add . --list
python scripts/smoke_install.py --agent codex
python scripts/smoke_install.py --agent claude-code
```

Проверьте trigger corpus на настоящем агенте, включая первый запуск навыка.
Структурный CI подтверждает полноту корпуса, но не заменяет наблюдение вызова
модели. Добавьте запросы и результат в checklist pull request.

Для общей trigger evaluation подготовьте blind suite и оцените ответы selector:

```shell
python scripts/trigger_evals.py prepare --output .trigger-evals/suite.json
python scripts/trigger_evals.py score \
  --predictions .trigger-evals/predictions.json \
  --json-output .trigger-evals/report.json \
  --markdown-output .trigger-evals/report.md
```

Selector может выбрать несколько навыков или ни одного. Не показывайте ему
исходные eval-файлы, ожидаемые labels, причины автора, предполагаемые ошибки и
прошлые отчёты. Фиксируйте provider/model, сохраняйте raw predictions и
проверяйте каждый false positive/negative. Рост score не оправдывает расширение
триггера, создающее неоднозначность.

`evals/release-holdout-vN.json` — append-only release evidence. Не читайте и не
запускайте активный holdout во время настройки описаний. Опубликованные версии
неизменяемы: создавайте `vN+1`, обновляйте имя, путь и canonical digest, храните
все версии. После заморозки описаний запускайте holdout и сравнивайте с baseline
той же версии и selector-конфигурации. Assertion digests должны совпадать.
Принятый отчёт сохраняется в `evals/baselines/`, указатель каталога обновляется.
Для недетерминированного selector используйте нечётное число не менее трёх
независимых blind runs и majority vote. Нельзя повторять один прогон до успеха
или отбрасывать корректные неуспешные наблюдения.

Критерий завершения: все команды проходят на каждой поддерживаемой ОС, а PR
checklist содержит доказательства затронутого навыка.

## Защита цепочки релиза

- Закрепляйте GitHub Actions полным SHA и оставляйте версию в комментарии.
  Обновления SHA проходят review через Dependabot.
- Выдавайте `GITHUB_TOKEN` только необходимые разрешения.
- Собирайте архивы через `scripts/build_release.py` и проверяйте `SHA256SUMS`.
- Публикуйте GitHub artifact attestations для каждого asset и проверяйте их
  командой `gh attestation verify <artifact> --repo kolabse/skills`.

- Не заменяйте существующий asset. Повторный workflow обязан подтвердить
  идентичные байты или завершиться ошибкой.
- Не перемещайте теги версий; исправление публикуется новой версией.

Критерий завершения: тег указывает на reviewed commit, assets совпадают с
`SHA256SUMS`, зависимости workflow закреплены неизменяемыми ссылками.
